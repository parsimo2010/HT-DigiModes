# Digital Radio Laboratory — Step-by-Step Development Plan

**Project:** M17 on-device firmware + host-assisted RADE BBFM  
**Prepared:** 2026-11-24  
**Audience:** Radio owner and Codex engineering agent  
**Status:** Plan; no hardware tests or flashing performed by this document  
**Recommended first development target:** Baofeng DM-1701  
**Second target:** incoming *Baofeng DM-1801*, hardware revision **not yet verified**

> **Project rule:** No firmware flash or experimental RF transmission is authorized by this plan alone. Establish backups, recovery, safety interlocks, and model-specific compatibility before each operation. Hardware measurements require a human at the bench.

## 0. Mission, scope, and operating model

The project has two related but distinct end goals:

1. **Standalone M17 on a handheld.** Implement M17 4800-symbol/s four-level FM modulation, framing, synchronization, FEC, Codec2 speech and PTT/audio/UI **on the radio**, without needing a computer once installed. Start with the DM-1701 because its STM32F405 + HR_C6000 + AT1846S architecture and open-firmware drivers are relatively well understood. A published M17 hardware-modification path exists, but **do not modify the PCB at the outset**.
2. **RADE BBFM with a computer.** Run the RADE neural encoder/decoder and initially the single-carrier PSK modem on an external Linux computer. Develop a controlled transport through a programming/accessory connector, with the radio handling FM receive/transmit and sample or symbol buffers. Prefer a **serial UART on a verified HR_C7000 DM-1801 Pro/current DM-1801** for this experiment if that is the delivered hardware; the **DM-1701 uses native USB, not UART, at its Kenwood-shaped connector**. Do not conflate physical connector shape with the electrical signals.

The LibreSDR is the **reference RF source, receiver and measurement instrument**, not a prerequisite second developer radio. The existing **DR-1801UV** is a separate Auctus A6-based stock reference; it is **not** the incoming DM-1801 and must never receive a DM-1801 firmware image.

**Known purchases / inventory (verify on receipt):** one DM-1701 and one labeled DM-1801 arriving from Radioddity; one LibreSDR already present; one DR-1801UV already present. Earlier plans for two C62 and two DM-32UV radios were canceled. No DB25-D is required for this plan.

### Success definitions

- **M17 TX proof:** LibreSDR captures a developer-radio emission with expected symbol rate, correct frame sync and valid M17 frames decoded by an independent reference; waveform and occupied bandwidth are recorded.
- **M17 RX proof:** developer radio decodes M17 frames generated by LibreSDR, including packet/frame error counts over a repeatable test set.
- **Standalone M17:** both receive and transmit intelligible speech and identification entirely on the DM-1701, measured with SDR as the other endpoint.
- **RADE transport proof:** host-to-radio and radio-to-host sample sessions complete with sequence and drop statistics and without stuck PTT, first in RAM/software loopback and then RF.
- **RADE RF proof:** a known RADE BBFM BPSK BER test passes in **both RF directions** separately; only then enable the neural codec and attempt real-time speech.

### Deliberate non-goals for the first iteration

Do not develop a new DMR stack, emulate trunking, modify both radios simultaneously, implement an SDR transceiver application from scratch, or attempt full-rate 9600-baud packet on an 8 kHz discriminator path. Do not assume M17 works via the native DMR PHY merely because it accepts arbitrary bits. Do not assume a factory Kenwood socket exposes audio samples or a modem without firmware work.

## 2. Safety and recovery gates by operation

1. **RF containment.** Use a 50-ohm dummy load rated above the selected radio's maximum RF power, a directional coupler or independently confirmed attenuation, and appropriate isolation. **Do not connect a 5 W handheld TX or any mobile TX directly to a LibreSDR RX port.** Calculate the worst-case input at the SDR in dBm and compare with the exact board's input rating before connection. Include connector/cable/coupler loss and a safety margin. Use minimum radio power; begin with receive-only SDR operation. Confirm TX channel permissions, amateur-service identification and emission limits before any radiated custom waveform.
2. **Interlock TX.** Any custom-firmware PTT command requires a bounded TX duration, fail-closed timeout, host-disconnect unkey, buffer-underrun unkey, and hardware/radio TOT. Default custom TX to *disabled* until an operator explicitly arms it.
3. **Preserve factory state.** Record model, FCC/board ID, bootloader/update procedure, firmware version, codeplug and any accessible entire flash/calibration/codec backup. Keep private backups offline/out of Git. A codeplug export is *not* a factory firmware or calibration backup.
4. **Recovery rehearsed.** Before first reflash, obtain the correct stock firmware or verified recovery backup and confirm how to enter the loader. Never use an image intended for another model, even if connectors/display look similar. Never erase the bootloader or calibration areas.
5. **Operator authorization.** For an application install, verify the named radio, bootloader layout, image checksum, write plan and stock recovery route. An explicit request to install that previewed image authorizes the corresponding write. For a conducted transmission apply the fixture requirements in item 1. The operator may also select a radiated measurement with separate antennas and local PTT. Record that choice and check the intended frequency, station identification, power and receiver setup for the transmission.

**Go/no-go record:** create `notes/gates.md` and log each pass with date, model/serial (private), evidence file names, measurement reference and approving human. Failed gates block the next RF/flash action; software-only work can proceed.

## 3. Session 1 — Arrival and factory baselines (human at bench)

**Estimated:** 90–180 min. **Goal:** preserve known-good devices, not install replacement firmware.

### Step 3.1 — Inventory and identify

- [ ] Unpack each radio; photograph front/back, label beneath battery, any FCC ID, charger, cable and plugs. Keep serial numbers private.
- [ ] Record the *literal* model names from label and menu; for DM-1801 specifically confirm whether it is **current/Pro HR_C7000** versus **original DM-1801 v1**. Do not infer from e-commerce titles alone.
- [ ] Record firmware version, hardware revision if shown, MCU/chip claims if available, and battery condition in `hardware/<model>/inventory.md`.
- [ ] Label the two programming cables **DM-1701 USB** and **DM-1801 unknown/UART only after verified**; do not cross-use merely because the two-pin plug fits.
- [ ] Verify battery chargers, screen, keypad, squelch and receive without modifying firmware.

### Step 3.2 — Stock analog/DMR smoke tests

- [ ] Program appropriate local amateur simplex frequencies with correct permitted power; document RX/TX values.
- [ ] Check analog FM reception; compare with existing DR-1801UV where practical. For RF TX tests, use a proper antenna on a permitted channel or a dummy load/test receiver arrangement.
- [ ] Check DMR voice between available compatible radios on the same frequency, color code, contact/talkgroup and timeslot where supported; **do not treat mismatched DMR firmware failures as a hardware failure**. The existing DR-1801UV is a potential reference.
- [ ] Note CPU lockups, audio, keying, unexpected prompts, and transmit-frequency offset. Do not upgrade factory firmware simply to obtain the newest version unless needed for recovery/compatibility.

### Step 3.3 — Computer interfaces and factory backups

- [ ] Download the official model-specific CPS and matching *stock firmware* from a verified source. Archive ZIPs with SHA-256 in a private directory.
- [ ] **DM-1701:** its Kenwood-shaped connector carries **native USB**. The original firmware/bootloader may enumerate as `0483:df11`; this **is not** a generic serial adapter. Use the correct no-converter DM-1701 USB cable. On Linux note USB descriptors with `lsusb`, `lsusb -v` as needed; do not send raw DFU writes.
- [ ] **DM-1801:** determine current/Pro vs v1 **before** connecting a USB-UART cable. On the current HR_C7000 version, RadioFoundry describes a 115200 8N1 UART on the programming connector and a PTT/host-RX shared line. Test read-only host communication using model-specific documented tools. Do not apply an arbitrary TTL voltage or wire a bare converter pin-to-pin based on Kenwood plug appearance.
- [ ] Save each factory **codeplug** unmodified using compatible CPS/qdmr. Keep checksum and an extra copy.
- [ ] When supported, use <https://radiofoundry.org/flash/index.html> **Back Up Now → Everything**, with the radio running stock firmware; retain the resulting ZIP and calibration/flash data **privately**. The available backup completeness depends on model/loader; read the generated report.
- [ ] Verify how to restore **this precise radio**. On the DM-1701, RadioFoundry documents power-on holding **PTT + SK1** (upper side key) for the loader; on the current DM-1801 Pro its loader also uses **PTT + SK1**, but **the serial loader erases the whole application including the codec**, so do not flash it until codec preservation is verified.
- [ ] Produce `notes/arrival-session.md`: hardware model decisions, backup filenames, hashes, cable IDs, stock smoke-test results, and open questions. No private backups in Git.

**Exit criteria:** both devices stock-functional or failures documented; DM-1801 architecture explicitly identified; backups verified; no reflashing undertaken. If identity is ambiguous, stop hardware work and photograph labels for review.

### Step 4.3 — Prove M17 entirely in GNU Radio

- [ ] Build `gr-m17` per its `README.md` (GNU Radio 3.10), and run `examples/m17_loopback.grc` first without RF.
- [ ] Run the noisy-channel example; log decoded frame count/error metrics.
- [ ] Open `examples/transmitterPLUTOSDR.grc`; it includes a **UHD USRP Sink** supporting B210-type hardware. Verify the **actual enabled sink**, center frequency, sample rate, interpolation and TX gain before any RF activation.
- [ ] Adapt `examples/receiverRTLSDR.grc` to **UHD USRP Source** for LibreSDR RX; do not transmit into a receiver without verified RF attenuation and isolation.
- [ ] Save a reference M17 complex I/Q file, frame-bit and symbol vectors, settings JSON and a spectrum screenshot. These are golden test fixtures.

### Step 4.4 — Prove RADE BBFM offline

- [ ] Follow `external/radae/BBFM.md` for any build dependencies and checkpoint availability.
- [ ] Run the project's `single_carrier().run_test(...)` self-test with documented noise and clock-offset settings.
- [ ] Run `sc_tx.py --ber_test` → `sc_rx.py --ber_test` from files/pipes. The reference uses **2400 symbols/s**, **9600 real samples/s**, **1500 Hz center audio frequency** and signed 16-bit output by default.
- [ ] Save short `t.int16`, decoded BER text and configuration. Only then test the neural encode/decode examples.
- [ ] Implement an SDR-only reference as **passband real audio → FM modulator → complex I/Q → SDR**, and reverse it with channel filtering, quadrature FM demodulation and resampling back to 9600 samples/s. Do **not** directly send the passband PSK waveform as complex RF IQ if the objective is BBFM interoperability with analog FM radios.

**Exit criteria:** M17 software loopback decodes; RADE BER self-test passes with settings recorded; LibreSDR accessible to UHD or a clear blocker filed. No developer-radio firmware modification required.

## 5. Session 3 — Capture stock-radio RF baselines

**Goal:** quantify RF performance before replacing firmware so later failures have a known comparison.

1. Decide an isolated RF arrangement (radio into load/coupler, SDR receive through rated attenuation) and produce a written attenuation calculation; if unavailable, collect only *receive-only* captures or attenuated off-air tests where safe.
2. Record at least one stable analog carrier from **each stock radio**: SDR I/Q file, observed carrier error, RF power setting, deviation (if known), spectrum and notes.
3. Record a known audio tone (e.g., 1 kHz) through stock analog FM where safely possible; measure pre-emphasis/relative frequency response and spectral occupancy.
4. Record a DMR call or test transmission if available, including RF burst envelope/timing and decoder status. Save both the radio's on-screen settings and SDR decode.
5. Run repeated short recordings so test-to-test variance is visible. **Do not invent a pass/fail RF quality threshold upfront**: derive practical targets from reference captures, standards and independent decoder performance.
6. Write `notes/baseline-rf.md` and a machine-readable `templates/capture-metadata.example.yaml` filled in for every capture.

**Exit criteria:** repeatable, non-clipped SDR captures with calibration/gain settings and expected FM/DMR behavior. Keep larger IQ data outside Git; keep metadata and checksums in Git.

## 7. M17 track — firmware-development milestones

### M17.1 — Establish host-generated golden frame vectors

- Generate known M17 sync/LSF/stream frames using the official reference, with deterministic fixed inputs, no RF.
- Store bit-level and dibit-level vectors (including CRC/FEC outcomes) and build independent unit tests that reproduce them.
- Add a host-only parser/framer module in the lab repo with clear license provenance; if planning to contribute to RadioFoundry MIT, **do not copy GPL code from OpenRTX, gr-m17 or other GPL projects**. Use public specs and independent tests as design references.

**Pass:** golden vectors round-trip without radio hardware, with documented frame timing and known test payloads.

### M17.2 — Compare two TX physical paths on DM-1701

**Path A: HR_C6000 native physical-layer TX.** RadioFoundry demonstrated arbitrary **288-bit / 30 ms** transmit blocks in PHY mode, equivalent to DMR's **4800 symbols/s** when packed as 4FSK dibits. This is *not* a claim of arbitrary baud, filters or deviation. Send known alternating levels, PRBS and sync-like sequences; capture with SDR; compare symbol mapping, spectral shape, deviation and continuity. Determine whether it can conform to M17's four deviation levels and RRC 0.5 shaping, **not just whether the bits are visible**.

**Path B: MOD1 register modulation.** RadioFoundry measured changing MOD1 offset at about 32.5–37.5k updates/s and a modest (~6-bit) modulation resolution; this can generate custom FM but is timing/noise limited. Implement a timer-paced finite waveform with jitter statistics and a strict PTT watchdog; do **not** start with continuous speech. Capture and compare symbol EVM/BER, deviation and occupied spectrum to Path A.

**Decision:** choose a TX PHY only if independently decoded bits/frames and measured spectral properties are acceptable. If neither works, evaluate the documented <https://github.com/M17-Project/DM-1701_mod> PCB route **as a separate opt-in hardware branch**, not as an unrecorded change.

### M17.3 — Prove receive path and frame decoding

- Probe HR_C6000's ungated RX RAM / 8 kHz FM audio and any raw PHY receive/test mode. Record full effective audio response, particularly >3 kHz, and sample timestamps/gaps.
- Generate known M17 bursts on LibreSDR, with clock and carrier offsets swept independently. Feed the DM-1701 in a safe RF arrangement.
- Perform sync detection, dibit timing recovery, FEC and frame logging on radio **without Codec2** first. At 4800 symbols/s and 8 kHz input, there are only **1.67 samples/symbol**, so this is a major go/no-go technical risk.
- Use BER/FER and false-sync counts instead of subjective audio as acceptance metrics. Record limitations and failure ranges; do not hide an RX limitation behind a perfect transmitter.

**Pass:** reliably decode valid M17 frames from SDR with repeatable BER/FER measurements at controlled signal levels and offsets.

### M17.4 — On-device Codec2, UI, audio and interoperability

- Measure code size, RAM, CPU and latency. Add Codec2 through legally compatible dependency choices and document license obligations.
- Implement 40 ms framing/audio pacing, receive playback, mic capture, clear channel/PTT, ID/callsign setup, TOT and failure handling.
- Validate transmitted and received audio separately against gr-m17 before attempting a live exchange.
- Test startup, idle RX, TX, channel switch, low battery, host disconnect and decoder reset. Confirm radio still functions in normal FM/DMR modes.

**Pass:** standalone bidirectional M17 intelligible voice against the SDR, correct identifiers, bounded PTT, repeatable measurements and a tested fallback to known-good firmware.

## 8. RADE BBFM track — host computer + radio bridge

### RADE.1 — Define the transport before editing firmware

**First preferred board:** delivered DM-1801 **only if** hardware is verified current/Pro HR_C7000 and serial loader/calibration protected; otherwise prototype on DM-1701 native USB. Consider analog AIOC/sound-card tests on DR-1801UV as a non-firmware fallback.

- Define an abstract `BasebandTransport` host API supporting **either** native USB CDC (DM-1701) or true UART (current DM-1801 Pro), and board-specific radio drivers underneath. The physical Kenwood-shaped connector must not determine the protocol.
- **Minimal commands:** `HELLO/CAPS`, `GET_STATUS`, `SET_RX`, `ARM_TX`, `START_TX`, `TX_BLOCK`, `STOP_TX`, `RX_BLOCK`, `GET_COUNTERS`, `RESET_COUNTERS`, `PING`. A host protocol must reject unsupported mode/rate and persistent changes.
- **Binary framing proposal** (versioned, to review): `magic | protocol_version | type | flags | sequence_u32 | sample_counter_u32 | length_u16 | payload | CRC32`. Include payload format, signedness, little-endian semantics and maximum length in an ADR. Consider COBS/SLIP-like framing only after simulating noise/truncation.
- Device-side per-session ring buffers plus underrun/overrun/drop/duplicate/CRC/re-key counters. Receiver samples carry a sample counter so the host can reconstruct gaps. Never silently duplicate samples to conceal underruns.
- PTT watchdog: require periodic host keepalives; unkey immediately on timeout/underrun/serial fault/host disconnect; hard independent TOT. Local PTT and emergency priority preserved.

### RADE.2 — Throughput and audio feasibility gate

For **115200 8N1 UART**, the theoretical user-byte maximum is **11520 B/s**, before framing, flow control or debug traffic. Confirm by measurement, not optimism:

| Format | Rate, one direction | Feasibility at 115200 8N1 |
|---|---:|---|
| 8 kHz × 8-bit mono | 8000 B/s | Potentially feasible **half duplex**, with modest framing overhead and robust buffering |
| 8 kHz × 16-bit mono | 16000 B/s | **Not feasible continuously** |
| 9.6 kHz × 16-bit mono | 19200 B/s | **Not feasible continuously** |
| M17 4800 dibits/s packed | 1200 B/s | Transport easy; RF PHY still challenging |

The RADE reference produces **9600 samples/s real 16-bit audio** for **2400-symbol/s** single-carrier passband PSK. Convert to an internally supported rate (initially **8000 samples/s**) using measured FIR resampling and **8-bit quantization only if needed** for UART. Offline compare BER against the unquantized reference and measure the RX/FM passband. Be prepared to use a lower-bandwidth mode, host DSP changes, or DM-1701 USB if BER is unacceptable.

The *current DM-1801 Pro* transmit route is **board-specific**: RadioFoundry reports that prompt FIFO alone did not modulate RF and used codec mixer settings to inject APRS tones. Start with that known-good test, then attempt a low-deviation sampled test tone; verify any receive sample extraction separately. **Do not assume the mixer supports clean, arbitrary PSK audio without measurement.**

### RADE.3 — Safe host-only framing test

- Write pure-host encoder, parser, checksum, packet-loss model and ring-buffer simulator. Use deterministic pseudo-random sample blocks and a fake serial endpoint.
- Unit test truncated/duplicate/reordered packets, baud-rate stalls, host restarts, partial frames, counter wrap and watchdog timeout. Make `ARM_TX` expire quickly; default state must always be receive-only.
- Build a CLI that prints real measured throughput with block size, occupancy, overruns, serial framing/CRC errors and latency histograms. No radio required.

**Pass:** one-way 8000 B/s payload sustained for a measured duration with headroom and no unaccounted drops; injected fault cases reliably unkey in simulation.

### RADE.4 — Device audio capture, injection and offline RF BER

- In a gated firmware branch, capture **received 8 kHz samples** from a verified RX path and send them to host with counters. Test against a known SDR FM tone and silence; verify de-emphasis/filter settings, fixed high-pass characteristics, quantization and squelch gating.
- Transmit generated low-level test tone through the confirmed board's FM input route and capture via SDR. Calibrate deviation and clipping before any 2400-symbol/s waveform.
- Reproduce `sc_tx.py --ber_test` passband waveform; resample/quantize/stream it into the radio and use LibreSDR's quadrature FM receiver plus `sc_rx.py --ber_test` to report BER. Reverse directions with LibreSDR as TX and host `sc_rx.py` reading radio RX blocks.
- Compare BER vs deviation, audio-center frequency, input gain, sample timing, carrier error and RF level. Never call a successful one-way decode a bidirectional working mode.

**Pass:** known test data decodes over RF in both separate directions with captured BER and no unreported sample gaps or unsafe keying.

### RADE.5 — Neural speech and real-time use

- Only after BER gate, run the pretrained RADE BBFM neural model against recorded test audio. Validate reconstructed quality and log model/checkpoint hash.
- Add buffering and scheduling for real-time mic/speaker operation, keeping the radio strictly half duplex. Measure end-to-end latency and underrun incidence under CPU/network load.
- Document a computer-to-radio setup procedure, pinout, cable identifiers, channel settings and safe recovery. Do not promise realtime stability until measured.

**Pass:** repeatable two-way test sessions with intelligible reconstructed speech, bounded TX duration and no significant unexplained packet loss.

**Ignore and protect:** `private/`, `backups/`, `calibration/`, `codeplugs/`, `codecs/`, firmware dumps, `*.iq`, `*.cfile`, `*.raw`, large `*.bin`, `*.pth`, and any radio personal IDs/serials, log files with identifiers or private RF capture metadata. Public test-vector files can be deliberately allowlisted by extension and size after review. Hashes and neutral metadata may be committed.

**Licensing:** RadioFoundry is MIT; gr-m17/OpenRTX include GPL components and Codec2 licensing is separate; RADE's files have their own licenses. Never copy GPL source into a MIT-only RadioFoundry contribution without an explicit license/architecture decision. Keep reference applications outside the lab repo unless permission/compatibility is clear. Stock AMBE codec and radio firmware dumps remain private.

## 11. Capture and measurement protocol

For each RF session record:

- UTC timestamp; test ID; transmitting and receiving devices and serial-number **aliases**, not private serials.
- Model, hardware version, firmware build git SHA and modulation approach (native PHY, MOD1, codec mixer, SDR reference).
- Frequencies, channel width, RF power setting, deviation, encoder/frame parameters, sample rate and gain.
- Dummy load rating, coupler losses, attenuator values and calculated worst-case SDR input power (dBm).
- SDR make/model, UHD version, FPGA image SHA, center frequency, sample rate, gain, reference clock, TX/RX antenna port.
- Captured IQ/audio/test vectors with file sizes and SHA-256 hashes; git-ignored paths or external storage reference.
- BER/FER/sync rate, packet-drop and underrun counters, carrier offset, occupied bandwidth, timing jitter.
- Any surprise, manual intervention, firmware fallback, or incomplete validation. Distinguish `measured`, `simulated`, and `hypothesis`.

For M17 and RADE compare transmissions at the **same bench geometry and equipment settings**, except deliberately swept parameters. A failed decode is data: preserve it with context.

## 13. Key technical decisions still open

- Does the delivered **DM-1801** use current HR_C7000 hardware or older NXP hardware? This gates its entire firmware and connector plan.
- Does DM-1701 M17 TX work without PCB modification: native HR_C6000 PHY vs MOD1 software waveform? Measure both.
- Can either radio receive acceptable 4800-symbol/s M17 with its accessible samples or native PHY? It must be demonstrated.
- Can RADE BBFM tolerate 9.6→8 kHz resampling and 8-bit quantization, the radio audio response and the tested UART headroom? Offline and RF BER must answer this.
- Is a true USB-to-UART connection available on the selected radio, or should the bridge use DM-1701 native USB? The connector alone does not decide.
- What licensing structure allows reuse of open DSP algorithms without making an incompatible contribution upstream?
